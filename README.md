# TDPrinter Care — Repair Ticketing System (Prototype)

โปรแกรมต้นแบบ (working prototype) ของระบบบริหารจัดการงานซ่อม ตามสเปคที่กำหนด: 4 สิทธิ์ผู้ใช้งาน, ฐานข้อมูล 6 ตาราง, โฟลว์สถานะ 6 ขั้น, Kanban board, คลังอะไหล่พร้อมระบบอนุมัติเบิกของราคาสูง, และหน้าเช็กสถานะสาธารณะสำหรับลูกค้า

รันด้วย **Python มาตรฐาน + SQLite + Jinja2 เท่านั้น** ไม่ต้องพึ่ง Django/Flask/Node — เพื่อให้ติดตั้งและรันได้ทันทีแทบทุกเครื่อง

## วิธีติดตั้งและรัน

ต้องมี Python 3.9+ ในเครื่อง

```bash
cd repair-ticket-system
pip install -r requirements.txt
python app.py
```

เปิดเบราว์เซอร์ไปที่ **http://localhost:8000**

ครั้งแรกที่รัน ระบบจะสร้างไฟล์ฐานข้อมูล `repair.db` และใส่ข้อมูลตัวอย่าง (ลูกค้า, เครื่องพิมพ์, อะไหล่, ผู้ใช้งาน) ให้อัตโนมัติ

> ถ้าเคยรัน `app.py` จากเวอร์ชันก่อนหน้ามาแล้ว (มีไฟล์ `repair.db` เก่าอยู่) ให้ลบ `repair.db` ทิ้งก่อนรันใหม่ทุกครั้งที่อัปเดตโค้ด — เวอร์ชันล่าสุดเพิ่มคอลัมน์ `is_active` ในตาราง Users, ตาราง `Ticket_Media`, คอลัมน์ `labor_fee` ใน Spare_Parts/Service_Logs, และตาราง `Quotations` / `Quotation_Items` ใหม่

ไฟล์ที่อัปโหลดจะถูกเก็บไว้ในโฟลเดอร์ `uploads/` (สร้างอัตโนมัติ) แยกตามเลขที่ตั๋ว — โฟลเดอร์นี้ไม่ได้อยู่ใน git และไม่ควร commit

## สิ่งที่ทำได้ในตัวต้นแบบนี้

- **Login แยกสิทธิ์ 4 ระดับ** (Customer / Admin / Technician / Manager) ด้วย session cookie
- **Customer:** แจ้งซ่อมใหม่พร้อม**เลือกสาขาที่ต้องการเข้ารับบริการจากแผนที่แบบอินเทอร์แอกทีฟ** (คลิกหมุดบนแผนที่หรือการ์ดสาขาก็ได้ ระบบจะบังคับเลือกถ้ามีสาขาในระบบ), **แนบรูปภาพได้สูงสุด 10 รูป และวิดีโอ 1 คลิป (ไม่เกิน 10 MB)**, ดูรายการ/รายละเอียดตั๋วของตัวเอง (พร้อมสาขาที่เลือก), ดูไทม์ไลน์สถานะ, ประเมิน CSAT หลังปิดงาน
- **Public tracking page** (`/track`): กรอก Serial Number แล้วดูไทม์ไลน์ได้โดยไม่ต้อง login (ไม่ต้องผูกบัญชี)
- **Admin:** Dashboard สรุปตัวเลข, Kanban board ลากเปลี่ยนสถานะ/มอบหมายช่างได้ (ผ่านฟอร์ม), จัดการลูกค้า/เครื่องพิมพ์พร้อมเช็กวันหมดประกันอัตโนมัติ, **จัดการคลังอะไหล่แบบเต็ม** — เพิ่ม/ลบอะไหล่ได้ (ลบไม่ได้ถ้าเคยถูกเบิกใช้ในงานซ่อม ป้องกันประวัติ/ใบแจ้งหนี้เก่าพัง), เติมสต็อก, ตั้ง**ค่าบริการเปลี่ยนอุปกรณ์มาตรฐาน**ต่อชิ้น, **แนบรูปอะไหล่ได้ 1 รูปต่อชิ้น** (ตอนเพิ่มใหม่หรืออัปโหลด/เปลี่ยนทีหลังก็ได้), **จัดการผู้ใช้งาน** (`/admin/users`) — สร้างบัญชีทุกสิทธิ์ (admin/technician/manager/customer), แก้ไขชื่อ-สิทธิ์-รีเซ็ตรหัสผ่าน, ระงับ/เปิดใช้งานบัญชี, ลบบัญชี (ถ้ามีข้อมูลผูกอยู่ในระบบ เช่นช่างที่เคยรับงาน ระบบจะระงับให้แทนการลบเพื่อกันข้อมูลพัง) พร้อมกันลบ/ระงับบัญชีตัวเอง, **ผูกผู้ใช้งาน (staff) เข้ากับศูนย์บริการ**ที่สังกัดได้
- **จัดการศูนย์บริการ** (`/admin/centers`) — เพิ่ม/ลบสาขาได้ (ลบไม่ได้ถ้ามีพนักงานสังกัดอยู่), ระบุที่อยู่/เบอร์โทร/พิกัด (ละติจูด-ลองจิจูด) — ศูนย์ที่ระบุพิกัดจะขึ้นปักหมุดบนแผนที่ที่หน้า Dashboard โดยอัตโนมัติ (ใช้ Leaflet + OpenStreetMap ไม่ต้องมี API key)
- **Technician:** ดูงานที่ตัวเองรับผิดชอบ, อัปเดตสถานะงาน, บันทึกผลการซ่อม + เบิกอะไหล่ (ตัดสต็อกอัตโนมัติ) พร้อม**ปรับค่าบริการเปลี่ยนอุปกรณ์ได้เองต่องาน** (ระบบโชว์ค่ามาตรฐานของอะไหล่แต่ละชิ้นให้อ้างอิง), **ออกใบเสนอราคาให้ลูกค้า**ได้ไม่จำกัดจำนวนใบต่อตั๋ว — โดย**รายการในใบเสนอราคาต้องเลือกมาจากประวัติการซ่อม (Service_Logs) จริงเท่านั้น** ไม่ใช่พิมพ์ขึ้นมาลอยๆ (ระบบให้ติ๊กเลือกงาน/อะไหล่ที่เคยบันทึกไว้ แล้วปรับราคาที่จะเสนอได้ก่อนออกใบ)
- **Manager:** Dashboard เดียวกับ Admin, อนุมัติ/ปฏิเสธการเบิกอะไหล่ราคาสูง (ค่าเริ่มต้น > 2,000 บาทต่อรายการ, แก้ไขได้ที่ `HIGH_COST_APPROVAL_THRESHOLD` ใน `db.py`), รายงาน CSAT เฉลี่ย
- **ใบแจ้งหนี้อัตโนมัติ:** เมื่อตั๋วเปลี่ยนเป็นสถานะ Resolved/Closed ระบบจะรวมรายการซ่อมทั้งหมด (ค่าอะไหล่ + ค่าบริการต่อรายการ) เป็นใบแจ้งหนี้พร้อมยอดรวมสุทธิ แสดงให้ทั้งลูกค้า ช่าง และ Admin/Manager เห็นตรงกัน
- **ส่งออกใบเสนอราคา/ใบแจ้งหนี้เป็น PDF:** ทุกใบมีปุ่ม "🖨️ พิมพ์ / บันทึกเป็น PDF" เปิดหน้าจัดรูปแบบสำหรับพิมพ์โดยเฉพาะ (มีหัวเอกสาร โลโก้ร้าน เลขที่เอกสาร) กดพิมพ์แล้วเลือกปลายทางเป็น "Save as PDF" ในเบราว์เซอร์เพื่อบันทึกไฟล์ — ไม่ใช้ไลบรารีสร้าง PDF ฝั่งเซิร์ฟเวอร์เพราะรับประกันไม่ได้ว่าเครื่องที่รันจะมีฟอนต์ไทยติดตั้งไว้ (เห็นรายละเอียดในหัวข้อข้อจำกัด)
- **รูปภาพ/วิดีโอที่ลูกค้าแนบ:** ช่างที่ได้รับมอบหมาย, Admin, และ Manager เปิดดูได้ทั้งหมด (ผ่านหน้ารายละเอียดตั๋ว) — ลูกค้าคนอื่นหรือช่างที่ไม่ได้รับมอบหมายเข้าถึงไฟล์ไม่ได้ (บังคับสิทธิ์ที่ route `/media/<ticket_id>/<filename>`)
- **โฟลว์สถานะ 6 ขั้น** ตามสเปค: New → Diagnosing → Waiting for Parts → In Repair → Testing → Resolved/Closed

ทดสอบไหลงานครบวงจรแล้ว: ลูกค้าแจ้งซ่อม → แอดมินมอบหมายช่าง → ช่างเบิกอะไหล่ราคาสูง (เข้าคิวรออนุมัติ, ยังไม่ตัดสต็อก) → ผู้จัดการอนุมัติ (ตัดสต็อกจริง) → ช่างปิดงาน → ลูกค้าประเมิน CSAT → ผู้จัดการดูรายงาน — ทำงานถูกต้องทุกขั้นตอน

## ข้อจำกัดของ Prototype (ที่ต้องทำเพิ่มก่อนใช้งานจริง)

- **รหัสผ่าน:** เก็บเป็น SHA-256 hash ธรรมดา ยังไม่มี salt/bcrypt — งานจริงควรใช้ bcrypt/argon2
- **Session:** เก็บใน memory ของโปรเซส รีสตาร์ทเซิร์ฟเวอร์แล้วทุกคนต้อง login ใหม่ — งานจริงควรย้ายไป Redis/DB
- **อัปโหลดรูป/คลิป:** ตอนนี้รับเป็นลิงก์ URL เท่านั้น ยังไม่มีระบบอัปโหลดไฟล์จริง
- **อัปโหลดไฟล์:** ตรวจสอบชนิดไฟล์จาก Content-Type ที่เบราว์เซอร์ส่งมาเท่านั้น (ยังไม่ตรวจ magic bytes), เก็บไฟล์ทั้งหมดไว้ในดิสก์เครื่องเดียว, และอ่านไฟล์ทั้งก้อนเข้าหน่วยความจำก่อนบันทึก — งานจริงควรอัปโหลดตรงไปยัง object storage (เช่น S3), จำกัดขนาด request ที่ตัว web server/reverse proxy ด้วย, และสแกนไวรัส
- **ใบเสนอราคา/ใบแจ้งหนี้:** ยังไม่มีสถานะอนุมัติจากลูกค้า (แค่ "แสดงให้เห็น" ตามที่ขอ), ไม่มีเลขที่เอกสารทางบัญชี/เลขกำกับภาษี, ใบแจ้งหนี้คำนวณสดจากประวัติการซ่อมทุกครั้งที่เปิดหน้า (ไม่ใช่เอกสารที่ fix ค้างไว้) — งานจริงควรมีการ "ปิดยอด" และเก็บสำเนาเอกสาร ณ วันที่ออกจริง
- **แผนที่ศูนย์บริการ:** โหลด Leaflet.js และแผนที่จาก OpenStreetMap ผ่านอินเทอร์เน็ต (CDN) ตอนเปิดหน้า Dashboard — ต้องมีอินเทอร์เน็ตตอนใช้งาน (ไม่ทำงานแบบออฟไลน์ล้วน), พิกัดต้องกรอกเองด้วยมือ (ยังไม่มีระบบแปลงที่อยู่เป็นพิกัดอัตโนมัติ)
- **PDF:** ใช้กลไก "พิมพ์จากเบราว์เซอร์ → Save as PDF" แทนการสร้างไฟล์ PDF ฝั่งเซิร์ฟเวอร์ เพราะไม่มีทางรับประกันได้ว่าเครื่องที่รัน `app.py` จะมีฟอนต์ไทยติดตั้งไว้ (ไลบรารีสร้าง PDF อย่าง reportlab ไม่ได้ดึงฟอนต์จากระบบปฏิบัติการอัตโนมัติ ถ้าไม่มีฟอนต์ไทยฝังในโค้ด ตัวอักษรไทยจะเพี้ยน/หายไปในไฟล์ PDF) วิธีนี้ใช้ฟอนต์ไทยจากเครื่องผู้ใช้เองผ่านเบราว์เซอร์ จึงถูกต้องเสมอและไม่มีปัญหาเรื่อง dependency เพิ่มเติม
- **Line Messaging API:** ยังไม่ได้เชื่อมต่อ (ตามสเปคข้อ 5) — จุดที่ควรเพิ่มคือตอนสร้าง/ปิดตั๋ว ให้ยิง webhook ไปหา Line OA
- **Kanban:** เปลี่ยนสถานะผ่านฟอร์ม dropdown ยังไม่ใช่ drag-and-drop จริง (ต้องเพิ่ม JS)
- **ฐานข้อมูล:** ใช้ SQLite (ไฟล์เดียว) เหมาะกับการทดสอบ/เดโม เมื่อจะขึ้น production ควรย้ายไป PostgreSQL ตามสเปคที่แนะนำ (โครงสร้างตาราง schema.sql ใกล้เคียงกันมาก แปลงไม่ยาก)
- ไม่มีการตรวจสอบสิทธิ์แบบละเอียด (เช่น CSRF token) — เหมาะสำหรับรันในเครื่อง/เดโมเท่านั้น ไม่ควรเปิดสู่อินเทอร์เน็ตสาธารณะตรงๆ
