# TD ServicePro — Repair Ticketing System (Prototype)

โปรแกรมต้นแบบ (working prototype) ของระบบบริหารจัดการงานซ่อม ตามสเปคที่กำหนด: 4 สิทธิ์ผู้ใช้งาน, ฐานข้อมูล 6 ตาราง, โฟลว์สถานะ 6 ขั้น, Kanban board, คลังสินค้าพร้อมระบบอนุมัติเบิกของราคาสูง, และหน้าเช็กสถานะสาธารณะสำหรับลูกค้า

รันด้วย **Python มาตรฐาน + PostgreSQL + Jinja2** ไม่ต้องพึ่ง Django/Flask/Node — dependency ภายนอกมีแค่ Jinja2 (templating) และ psycopg2 (ไดรเวอร์เชื่อมต่อ PostgreSQL)

> **ย้ายมาจาก MySQL อยู่หรือเปล่า?** ถ้า deploy นี้เคยใช้ MySQL มาก่อนและมีข้อมูลจริงอยู่แล้ว
> ห้ามทำตามขั้นตอนด้านล่างตรงๆ — ดู [`MIGRATION.md`](./MIGRATION.md) ก่อนเสมอ

## วิธีติดตั้งและรัน

ต้องมี Python 3.9+ และ PostgreSQL server (14 ขึ้นไป) ที่เข้าถึงได้ — จะรันเองในเครื่อง,
ใน Docker (ดูด้านล่าง), หรือใช้ PostgreSQL ที่มีอยู่แล้วก็ได้

```bash
cd repair-ticket-system
pip install -r requirements.txt
export PG_HOST=127.0.0.1
export PG_USER=tdprinter
export PG_PASSWORD=tdprinter_pw
export PG_DATABASE=tdprinter_care
python app.py
```

(ต้องสร้างผู้ใช้ PostgreSQL ด้วยสิทธิ์สร้างฐานข้อมูลไว้ก่อน เช่น
`CREATE USER tdprinter WITH PASSWORD 'tdprinter_pw' CREATEDB;`
— ตัวแอปจะสร้างฐานข้อมูล `tdprinter_care`, ตารางทั้งหมด, และ seed ข้อมูลตัวอย่างให้เองถ้ายังไม่มี)

เปิดเบราว์เซอร์ไปที่ **http://localhost:8000**

ไฟล์ที่อัปโหลดจะถูกเก็บไว้ในโฟลเดอร์ `uploads/` (สร้างอัตโนมัติ) แยกตามเลขที่ตั๋ว — โฟลเดอร์นี้ไม่ได้อยู่ใน git และไม่ควร commit

### รันด้วย Docker (แนะนำ — ได้ PostgreSQL มาด้วยในตัว)

มี `Dockerfile` + `docker-compose.yml` ให้พร้อมใช้งาน (รวม PostgreSQL service) ดูขั้นตอน
ละเอียด (build ตรงจาก GitHub, การเก็บข้อมูลถาวร, ตัวแปรแวดล้อม) ได้ใน
[`DOCKER.md`](./DOCKER.md) สรุปสั้น ๆ:

```bash
docker compose up -d --build
```

## สิ่งที่ทำได้ในตัวต้นแบบนี้

- **Login แยกสิทธิ์ 4 ระดับ** (Customer / Admin / Technician / Manager) ด้วย session cookie
- **Customer:** แจ้งซ่อมใหม่พร้อม**เลือกสาขาที่ต้องการเข้ารับบริการจากแผนที่แบบอินเทอร์แอกทีฟ** (คลิกหมุดบนแผนที่หรือการ์ดสาขาก็ได้ ระบบจะบังคับเลือกถ้ามีสาขาในระบบ), **แนบรูปภาพได้สูงสุด 10 รูป และวิดีโอ 1 คลิป (ไม่เกิน 10 MB)**, ดูรายการ/รายละเอียดตั๋วของตัวเอง (พร้อมสาขาที่เลือก), ดูไทม์ไลน์สถานะ, ประเมิน CSAT หลังปิดงาน
- **Public tracking page** (`/track`): กรอก Serial Number แล้วดูไทม์ไลน์ได้โดยไม่ต้อง login (ไม่ต้องผูกบัญชี)
- **Admin:** Dashboard สรุปตัวเลข, Kanban board ลากเปลี่ยนสถานะ/มอบหมายช่างได้ (ผ่านฟอร์ม), จัดการลูกค้า/เครื่องพิมพ์พร้อมเช็กวันหมดประกันอัตโนมัติ, **จัดการคลังสินค้าแบบเต็ม** (`/admin/inventory`) — เพิ่ม/แก้ไข/ลบสินค้าได้ (ลบไม่ได้ถ้าเคยถูกเบิกใช้ในงานซ่อม ป้องกันประวัติ/ใบแจ้งหนี้เก่าพัง), ค้นหาสินค้าได้จาก SKU/ชื่อ/รุ่นที่ใช้ร่วมกันได้, เติมสต็อก, ตั้ง**ค่าบริการเปลี่ยนอุปกรณ์มาตรฐาน**และ**ค่าคอมมิชชั่น**ต่อชิ้น, **ระบุศูนย์บริการที่เก็บสินค้าแต่ละชิ้นได้** (หรือปล่อยว่างไว้เป็นคลังกลาง), **แนบรูปสินค้าได้ 1 รูปต่อชิ้น** (ตอนเพิ่มใหม่หรืออัปโหลด/เปลี่ยนทีหลังก็ได้), **จัดการผู้ใช้งาน** (`/admin/users`) — สร้างบัญชีทุกสิทธิ์ (admin/technician/manager/customer), แก้ไขชื่อ-สิทธิ์-รีเซ็ตรหัสผ่าน, ระงับ/เปิดใช้งานบัญชี, ลบบัญชี (ถ้ามีข้อมูลผูกอยู่ในระบบ เช่นช่างที่เคยรับงาน ระบบจะระงับให้แทนการลบเพื่อกันข้อมูลพัง) พร้อมกันลบ/ระงับบัญชีตัวเอง, **ผูกผู้ใช้งาน (staff) เข้ากับศูนย์บริการ**ที่สังกัดได้
- **จัดการศูนย์บริการ** (`/admin/centers`) — เพิ่ม/ลบสาขาได้ (ลบไม่ได้ถ้ามีพนักงานสังกัดอยู่), ระบุที่อยู่/เบอร์โทร/พิกัด (ละติจูด-ลองจิจูด) — ศูนย์ที่ระบุพิกัดจะขึ้นปักหมุดบนแผนที่ที่หน้า Dashboard โดยอัตโนมัติ (ใช้ Leaflet + OpenStreetMap ไม่ต้องมี API key), **กำหนดประเภทเครื่องพิมพ์ที่แต่ละสาขารับซ่อมได้** (FDM / Resin / ทั้งสองแบบ) แก้ไขได้ตลอดแม้สร้างสาขาไปแล้ว — หมุดบนแผนที่จะขึ้นสีต่างกันตามประเภทที่รับซ่อม (ม่วง = รับทั้งคู่, น้ำเงิน = FDM เท่านั้น, ส้ม = Resin เท่านั้น) ทั้งที่หน้า Dashboard และหน้าเลือกสาขาตอนลูกค้าแจ้งซ่อม
- **Technician:** ดูงานที่ตัวเองรับผิดชอบ, อัปเดตสถานะงาน, บันทึกผลการซ่อม + เบิกอะไหล่ (ตัดสต็อกอัตโนมัติ) พร้อม**ปรับค่าบริการเปลี่ยนอุปกรณ์ได้เองต่องาน** (ระบบโชว์ค่ามาตรฐานของอะไหล่แต่ละชิ้นให้อ้างอิง), **ออกใบเสนอราคาให้ลูกค้า**ได้ไม่จำกัดจำนวนใบต่อตั๋ว — โดย**รายการในใบเสนอราคาต้องเลือกมาจากประวัติการซ่อม (Service_Logs) จริงเท่านั้น** ไม่ใช่พิมพ์ขึ้นมาลอยๆ (ระบบให้ติ๊กเลือกงาน/อะไหล่ที่เคยบันทึกไว้ แล้วปรับราคาที่จะเสนอได้ก่อนออกใบ)
- **Manager:** เห็นเฉพาะข้อมูลของศูนย์บริการที่ตัวเองสังกัดเท่านั้น (กำหนดจาก "ศูนย์บริการที่สังกัด" ในหน้าจัดการผู้ใช้งาน) — ครอบคลุม Dashboard (มีป้ายกำกับ "ศูนย์บริการ" บอกชัดเจนว่ากำลังดูของสาขาไหน), Kanban board, รายละเอียด/แก้ไขตั๋วซ่อม (เปิดตั๋วศูนย์อื่นไม่ได้ ขึ้น 403), ลูกค้า/เครื่องพิมพ์, คลังสินค้า (เห็นสินค้าของศูนย์ตัวเอง + สินค้าคลังกลางที่ใช้ร่วมกันทุกสาขา), อนุมัติ/ปฏิเสธการเบิกอะไหล่ราคาสูง (ค่าเริ่มต้น > 2,000 บาทต่อรายการ, แก้ไขได้ที่ `HIGH_COST_APPROVAL_THRESHOLD` ใน `db.py`), รายงาน CSAT เฉลี่ย, และเมนูรายงานทั้งหมด — ถ้า manager ยังไม่ถูกกำหนดศูนย์บริการ ระบบจะไม่แสดงข้อมูลใดๆ จนกว่าแอดมินจะกำหนดให้ (ไม่ fallback ไปเห็นข้อมูลทุกสาขา) ส่วน **Admin เห็นข้อมูลทุกศูนย์บริการเหมือนเดิม ไม่ถูกจำกัด**
- **เมนูรายงาน** (`/admin/reports`, เข้าถึงได้ทั้ง Admin และ Manager) — เลือกช่วงวันที่ได้อิสระ แสดง 3 รายงาน: (1) ช่างซ่อม — จำนวนเคสที่ได้รับมอบหมาย/ปิดงานแล้ว และยอดค่าแรงรวมต่อคน (2) ปริมาณการซ่อมแยกตามศูนย์บริการ — จำนวนตั๋วทั้งหมด/ปิดงานแล้วต่อสาขา (3) ปริมาณการเบิกอะไหล่ — จำนวนและมูลค่าที่เบิกต่อ SKU เรียงจากเบิกเยอะสุด พร้อมปุ่มพิมพ์/บันทึกเป็น PDF
- **ใบแจ้งหนี้อัตโนมัติ:** เมื่อตั๋วเปลี่ยนเป็นสถานะ Resolved/Closed ระบบจะรวมรายการซ่อมทั้งหมด (ค่าอะไหล่ + ค่าบริการต่อรายการ) เป็นใบแจ้งหนี้พร้อมยอดรวมสุทธิ แสดงให้ทั้งลูกค้า ช่าง และ Admin/Manager เห็นตรงกัน
- **ส่งออกใบเสนอราคา/ใบแจ้งหนี้เป็น PDF:** ทุกใบมีปุ่ม "🖨️ พิมพ์ / บันทึกเป็น PDF" เปิดหน้าจัดรูปแบบสำหรับพิมพ์โดยเฉพาะ (มีหัวเอกสาร โลโก้ร้าน เลขที่เอกสาร) กดพิมพ์แล้วเลือกปลายทางเป็น "Save as PDF" ในเบราว์เซอร์เพื่อบันทึกไฟล์ — ไม่ใช้ไลบรารีสร้าง PDF ฝั่งเซิร์ฟเวอร์เพราะรับประกันไม่ได้ว่าเครื่องที่รันจะมีฟอนต์ไทยติดตั้งไว้ (เห็นรายละเอียดในหัวข้อข้อจำกัด)
- **รูปภาพ/วิดีโอที่ลูกค้าแนบ:** ช่างที่ได้รับมอบหมาย, Admin, และ Manager เปิดดูได้ทั้งหมด (ผ่านหน้ารายละเอียดตั๋ว) — ลูกค้าคนอื่นหรือช่างที่ไม่ได้รับมอบหมายเข้าถึงไฟล์ไม่ได้ (บังคับสิทธิ์ที่ route `/media/<ticket_id>/<filename>`)
- **โฟลว์สถานะ 6 ขั้น** ตามสเปค: New → Diagnosing → Waiting for Parts → In Repair → Testing → Resolved/Closed

ทดสอบไหลงานครบวงจรแล้ว: ลูกค้าแจ้งซ่อม → แอดมินมอบหมายช่าง → ช่างเบิกอะไหล่ราคาสูง (เข้าคิวรออนุมัติ, ยังไม่ตัดสต็อก) → ผู้จัดการอนุมัติ (ตัดสต็อกจริง) → ช่างปิดงาน → ลูกค้าประเมิน CSAT → ผู้จัดการดูรายงาน — ทำงานถูกต้องทุกขั้นตอน

## ข้อจำกัดของ Prototype (ที่ต้องทำเพิ่มก่อนใช้งานจริง)

- **รหัสผ่าน:** เข้ารหัสด้วย PBKDF2-HMAC-SHA256 + salt สุ่มต่อผู้ใช้ (260,000 รอบ) แล้ว — บัญชีเก่าที่เคย hash แบบ SHA-256 เปล่าๆ จะอัปเกรดอัตโนมัติทันทีที่ login สำเร็จครั้งถัดไป
- **Session:** หมดอายุอัตโนมัติ (ไม่ใช้งาน 8 ชม. หรือครบ 24 ชม.) และเก็บใน memory ของโปรเซส รีสตาร์ทเซิร์ฟเวอร์แล้วทุกคนต้อง login ใหม่ — ถ้าจะ scale หลาย instance ควรย้ายไป Redis/DB
- **CSRF / brute-force login:** มีการป้องกันแล้ว — ทุกฟอร์มที่ล็อกอินแล้วต้องแนบ csrf_token ที่ตรงกับ session, และล็อกบัญชีชั่วคราว 15 นาทีหลัง login ผิด 5 ครั้งต่อคู่ IP+username
- **อัปโหลดรูป/คลิป:** ตอนนี้รับเป็นลิงก์ URL เท่านั้น ยังไม่มีระบบอัปโหลดไฟล์จริง
- **อัปโหลดไฟล์:** ตรวจสอบชนิดไฟล์จาก Content-Type ที่เบราว์เซอร์ส่งมาเท่านั้น (ยังไม่ตรวจ magic bytes), เก็บไฟล์ทั้งหมดไว้ในดิสก์เครื่องเดียว, และอ่านไฟล์ทั้งก้อนเข้าหน่วยความจำก่อนบันทึก — งานจริงควรอัปโหลดตรงไปยัง object storage (เช่น S3), จำกัดขนาด request ที่ตัว web server/reverse proxy ด้วย, และสแกนไวรัส
- **ใบเสนอราคา/ใบแจ้งหนี้:** ยังไม่มีสถานะอนุมัติจากลูกค้า (แค่ "แสดงให้เห็น" ตามที่ขอ), ไม่มีเลขที่เอกสารทางบัญชี/เลขกำกับภาษี, ใบแจ้งหนี้คำนวณสดจากประวัติการซ่อมทุกครั้งที่เปิดหน้า (ไม่ใช่เอกสารที่ fix ค้างไว้) — งานจริงควรมีการ "ปิดยอด" และเก็บสำเนาเอกสาร ณ วันที่ออกจริง
- **แผนที่ศูนย์บริการ:** โหลด Leaflet.js และแผนที่จาก OpenStreetMap ผ่านอินเทอร์เน็ต (CDN) ตอนเปิดหน้า Dashboard — ต้องมีอินเทอร์เน็ตตอนใช้งาน (ไม่ทำงานแบบออฟไลน์ล้วน), พิกัดต้องกรอกเองด้วยมือ (ยังไม่มีระบบแปลงที่อยู่เป็นพิกัดอัตโนมัติ)
- **PDF:** ใช้กลไก "พิมพ์จากเบราว์เซอร์ → Save as PDF" แทนการสร้างไฟล์ PDF ฝั่งเซิร์ฟเวอร์ เพราะไม่มีทางรับประกันได้ว่าเครื่องที่รัน `app.py` จะมีฟอนต์ไทยติดตั้งไว้ (ไลบรารีสร้าง PDF อย่าง reportlab ไม่ได้ดึงฟอนต์จากระบบปฏิบัติการอัตโนมัติ ถ้าไม่มีฟอนต์ไทยฝังในโค้ด ตัวอักษรไทยจะเพี้ยน/หายไปในไฟล์ PDF) วิธีนี้ใช้ฟอนต์ไทยจากเครื่องผู้ใช้เองผ่านเบราว์เซอร์ จึงถูกต้องเสมอและไม่มีปัญหาเรื่อง dependency เพิ่มเติม
- **Line Messaging API:** ยังไม่ได้เชื่อมต่อ (ตามสเปคข้อ 5) — จุดที่ควรเพิ่มคือตอนสร้าง/ปิดตั๋ว ให้ยิง webhook ไปหา Line OA
- **Kanban:** เปลี่ยนสถานะผ่านฟอร์ม dropdown ยังไม่ใช่ drag-and-drop จริง (ต้องเพิ่ม JS)
- **ฐานข้อมูล:** ใช้ PostgreSQL (ผ่าน psycopg2) รองรับการรันหลาย instance ของตัวแอปพร้อมกันได้ (scale แนวนอน) เพราะข้อมูลอยู่กลางที่ PostgreSQL ไม่ได้อยู่ในไฟล์เดียวแบบเดิม — สิ่งที่ยังต้องทำเพิ่มก่อน production จริงคือ backup อัตโนมัติ (pg_dump/WAL archiving), ปรับ connection pooling (ตอนนี้เปิด/ปิด connection ใหม่ทุก request), และย้าย session จากหน่วยความจำไป Redis ถ้าจะ scale หลาย instance
- **ก่อน deploy จริง** ต้องตั้งค่าไฟล์ `.env` (ก็อปจาก `.env.example`) ให้ครบ โดยเฉพาะรหัสผ่าน PostgreSQL ใหม่, `SEED_DEMO_DATA=0`, `INITIAL_ADMIN_USERNAME`/`INITIAL_ADMIN_PASSWORD`, และต้องรันหลัง reverse proxy ที่ทำ HTTPS ให้เสมอ (ดูรายละเอียดใน DOCKER.md หัวข้อ "หมายเหตุสำหรับการใช้งานจริง") — ถ้ากำลังย้ายจาก MySQL เดิมที่มีข้อมูลจริงอยู่แล้ว ให้ทำตาม [`MIGRATION.md`](./MIGRATION.md) แทนการติดตั้งใหม่ตรงๆ
